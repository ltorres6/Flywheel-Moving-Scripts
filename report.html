What to expect on your site

  • One session at a time (WORKERS=1): about 2.0–2.2x faster. This comes from making 58% fewer requests. Most of what's left are the moves themselves, which can't be avoided.
  • Default 4 workers: about 5.6–6.9x faster on our test site. The extra gain over WORKERS=1 comes from overlapping request round trips. Our runs went from a workstation to the site with a median of ~45 ms per request. If your runner sits closer to the server, every request is faster for both versions and the parallel gain is somewhat smaller; if it's farther away, it's larger.
  • Runs where little needs moving gain the most. For a session that is skipped (incomplete patient info, nothing uploaded), the original makes 4 requests and the optimized script makes 1–2. Scheduled runs over mostly processed projects fall in this case.
  • Larger projects gain more server headroom. The original's server CPU per 100 sessions roughly doubled from 30 to 600 sessions per project (59 to 114 CPU-s). The optimized script stayed at 36–40.

Each large-data configuration was run once; run-to-run timing on a shared site varies by about 10%. Server CPU for the optimized script comes from a run that did not yet include the final emptiness check and the session read used for reader tasks; those add about 15% more requests, all small reads (25–30 ms each). The WORKERS=1 CPU figure is from a one-at-a-time run making the same reads. Reader tasks were not created in these test runs: we don't have your utils/tasks.py, so each create_task call was recorded instead. Its own API calls are the same in both versions and are not in the timings.

Before you run it

  1. Copy your four reader-task values from your current handle_visit1_session into OCT_ASSIGNEE, OCT_PROTOCOL_LABEL, FP_ASSIGNEE and FP_PROTOCOL_LABEL at the top of the optimized script. If any is empty, the script prints a warning when it starts.
  2. Keep utils/tasks.py next to the script, as today. The script needs the same packages as before (flywheel-sdk and fw-client; backoff is installed with fw-client).
  3. The API key is read from the same file path as before. FW_API_KEY_PATH or FW_API_KEY can point elsewhere, and SRC_GROUP / CERT_GROUP change the groups.
  4. Check the first line it prints: the site, the groups, the number of workers and where the key came from.
  5. WORKERS=1 runs one session at a time with the lowest load on the server; the default is 4.
  6. Ctrl-C stops the run after the sessions already in progress finish. If any session fails, the script lists it at the end and exits with an error; running it again picks up whatever is left.

Equivalence with your script

We ran your script and the optimized script on identical copies of the test data and compared the results: every project, subject, session, acquisition and file in all four destination and source projects, and every create_task call (which acquisition, which destination session, protocol label and assignee). At 300 sessions, with four sessions handled at a time, every container and all 160 reader tasks matched. The one difference: where two Uploader Acknowledgement sessions merged, which of the two files got the _2 suffix differed in 3 of 10 projects, because the order in which parallel sessions arrive varies. The same files ended up in the same session. The test data covers all four session types, OCT original/companion pairs (including a session with two originals), lone OCT and FP acquisitions, two Uploader Acknowledgement sessions in one project (the second merges into the first), sessions with nothing uploaded, incomplete patient info, and existing destination containers so every rename path runs.

Intentional differences (all listed under Fixes):

  • DQE no longer gets an empty subject for every source subject, and Certification Review no longer gets one for a certification session with no files (F5).
  • A Patient Information session with no acquisitions is moved but not then deleted from Participant History (F5).
  • Rename suffixes are _2, _3, … instead of a millisecond value (F3).
  • One failed session no longer stops the run (F6), and Ctrl-C lets sessions already in progress finish.
  • Sessions are handled four at a time, so when two labels collide in a destination, which one gets the _2 suffix can vary between runs.

How we measured

  • A Flywheel test site was seeded with synthetic data shaped like yours: digit-prefixed study projects, DQE, Participant History and Certification Review, all four session types, OCT original/companion pairs, and pre-existing destination conflicts so the rename paths run. Every run started from a fresh copy.
  • Every HTTP request was counted and timed on the client. On the server we read the API's per-route timings and the CPU used by the API, database and search index before and after each run, minus the site's idle load.
  • Each change was first tested on its own against the original, then all together.
  • Reader-task calls were recorded instead of creating tasks, so both versions' calls could be compared directly.

Changes

Ranked by the server time each change saves on its own. Requests and server time don't rank the same way: removing 582 cheap lookups (C4) saves less than removing 506 reads that follow a write (C1).

C1 Create without the follow-up read

project.add_subject() and subject.add_session() send a create request and then read the new container back. The script only needs the new id, which fw.add_subject() and fw.add_session() return directly. A container that was just created is also known to be empty, so its sessions and acquisitions never need to be listed.

Measured alone: 506 fewer requests, 17.0 s less server time per run (10 x 30).

Original

Optimized

C9 Process sessions in parallel (WORKERS, default 4)

Sessions are handled by a small pool of threads. Each session is read, planned and moved by one thread, so its moves always finish before its delete. Moves into the same destination wait for each other, so two sessions arriving together end up the same as when they are handled one after the other. Ctrl-C cancels sessions that have not started and lets the running ones finish. WORKERS=1 handles one session at a time.

Original
for session in sessions:
    handle(session)
Optimized
pool = ThreadPoolExecutor(WORKERS)
pool.submit(process_session, ...)

Small calls vs. project-wide listings

We also tested reading a whole project's acquisitions in one filtered call (GET /acquisitions?filter=parents.project=…) instead of once per session. It used 10–20% less total server time at our sizes, but each call got slower as projects grew, and smaller pages didn't help: each page pays a cost that grows with the size of the project.

Sessions per projectProject-wide listing, per callPer-session listing, per call
30 (~45 acquisitions)375 ms25 ms
150 (~225)1,920 ms25 ms
600 (~900)2,070 ms per 250-item page30 ms
900-acquisition project, page size 50 / 100 / 250700 / 1,130 / 2,440 ms 

Rule of thumb for other scripts: list a container's children by parent (session.acquisitions(), subject.sessions()) rather than filtered searches across a project or group, especially for projects that keep growing, like DQE.

Running in parallel

We compared the SDK's async_=True option, which sends calls on the SDK's own thread pool, with a plain ThreadPoolExecutor over sessions. async_ works for firing a batch of independent updates, but the reads before them still run one at a time; it reached about 5x. The thread pool overlaps reads and writes and reached 7–10x. The script uses the thread pool.

Parallel work doesn't reduce server work. It packs the same work into less time: with 4 workers the run uses about 5.3 cores across the server while it runs, against 1.8 for the original, for about 1/7 of the time.

If the script runs during busy hours or alongside imports and gear runs, WORKERS=1 still uses about a third of the original's server CPU and puts less pressure on the server at any moment than the original. We'd keep the worker count at 4 or below.

Checklist for other scripts

  1. Count requests per container. If a loop over sessions makes more than three or four calls each, look for repeats.
  2. Look up anything fixed (projects, groups, protocols) once, before the loop.
  3. Keep what you create or find in a dictionary and check it before asking the server.
  4. Don't reload after a write unless you need a server-computed field. Use fw.add_* when you only need the new id.
  5. Combine updates to the same container into one call.
  6. List children by parent rather than filtered project-wide searches, and page long lists.
  7. Add parallelism last, with a small worker count, and keep each container's steps in one thread.
  8. Make the script safe to re-run so a failure partway through doesn't need manual repair.
